## 00 - Orientation

Before writing a single analytical query you establish what is in the database and whether it is what you think it is.
In a regulated setting this is not optional: a data product is only as trustworthy as your ability to show *what it
contains* and *that the load was complete*. These two queries are the habit to build first.

### O-01 - Orient yourself: schema and constraints

`beginner`  `read-only`

**What you learn.** db.schema.visualization() draws the as-built model; SHOW CONSTRAINTS lists the integrity rules the database enforces.

**Why it matters in biopharma.** Auditors and new team members ask "what do you store and how is it linked?". The as-built schema is the honest answer, as opposed to the as-designed diagram in a slide. Constraints are the first-line data-integrity controls: they are what stops a duplicate batch number or lab ID from existing at all.

```cypher
CALL db.schema.visualization();
SHOW CONSTRAINTS;
```

**What to expect.** A graph of 17 labels and 34 relationship types. SHOW CONSTRAINTS returns 18 uniqueness constraints (one per key plus Employee.email).

### O-02 - Sanity counts after a load

`beginner`  `read-only`

**What you learn.** Grouping by labels(n)[0] and type(r) gives per-label and per-relationship-type counts without naming them.

**Why it matters in biopharma.** Reconciling record counts between source and target is the minimum completeness control for any GxP data load (the "Complete" and "Consistent" in ALCOA+). A pipeline that loads without reconciling is not finished.

```cypher
MATCH (n) RETURN labels(n)[0] AS label, count(*) AS nodes ORDER BY nodes DESC;
MATCH ()-[r]->() RETURN type(r) AS rel, count(*) AS rels ORDER BY rels DESC;
```

**What to expect.** 1,262 nodes and 5,601 relationships in total. Compare each row with the counts in cypher/post_load.cypher.

## 01 - Cypher foundations (SQL to Cypher, with the traps)

The earlier sections use Cypher before they explain it. This section goes back to the building blocks, on the same
biopharma graph, with the specific behaviours that catch people who know SQL: case-sensitive strings, `null` logic,
precedence, `WITH`, `OPTIONAL MATCH`, `UNWIND`, sort order. Every query ends in a **Pitfall**: the plausible wrong
version, and why it fails or quietly returns the wrong answer. Reading for correctness matters as much as writing,
because an open-book test will ask you to judge a query, not only to write one.

| SQL habit | Cypher |
|---|---|
| `FROM a JOIN b ON ...` | the pattern `(a)-[:REL]->(b)` in `MATCH` |
| `WHERE` | `WHERE`, or an inline map `{prop: value}` (equality only) |
| `<>` or `!=` | `<>` only |
| `LIKE 'x%'` / `'%x%'` | `STARTS WITH` / `CONTAINS`; `=~` for a regular expression (matches the whole string) |
| `GROUP BY` | none: non-aggregated `RETURN` items are the grouping key |
| `HAVING` | `WITH ... WHERE` |
| `LEFT JOIN` | `OPTIONAL MATCH` |
| `OFFSET n LIMIT m` | `SKIP n LIMIT m` |
| `CASE WHEN ...` | `CASE WHEN ...` (same) |
| `UNION [ALL]` | `UNION [ALL]` (same) |
| `IS NULL` | `IS NULL` (same; and a missing property is `null`) |
| `SELECT DISTINCT` | `RETURN DISTINCT` |
| row per list element (`unnest`) | `UNWIND` |

Two things to keep in mind throughout. Keywords are not case-sensitive, but labels, relationship types, property
names, variables and string values are. And a typo in a property name is not an error: it is `null`.

### F-01 - Equality is case-sensitive: toLower and friends

`beginner`  `read-only`  `exam: Cypher`

**What you learn.** String comparison with = is exact and case-sensitive, so a mismatch returns zero rows and no error; normalise with toLower() or toUpper() before comparing.

**Why it matters in biopharma.** Material, method and equipment names come from several systems (ERP, LIMS, QMS) with inconsistent capitalisation. Matching them safely is the first step of any cross-system lookup.

```cypher
MATCH (m:Material)
RETURN count(CASE WHEN m.name = 'cho production basal medium' THEN 1 END)          AS exactMatch,
       count(CASE WHEN toLower(m.name) = 'cho production basal medium' THEN 1 END) AS lowerMatch;

MATCH (m:Material)
WHERE toLower(m.name) = 'cho production basal medium'
RETURN m.name AS name;
```

**What to expect.** Statement 1 returns one row: exactMatch 0, lowerMatch 1. Statement 2 returns the single material 'CHO Production Basal Medium'.

**Pitfall.** Wrapping a property in a function such as toLower() usually stops a regular (range) index from being used, so on large data you pay for a scan; the usual fixes are a text index or storing a normalised copy of the property.

**In the manual.** Cypher manual: Functions > String functions (toLower, toUpper); Operators > Comparison operators.

### F-02 - AND, OR, NOT and precedence: parenthesise

`beginner`  `read-only`  `exam: Cypher`

**What you learn.** AND binds tighter than OR (and NOT tighter than AND), exactly as in SQL; mixed conditions without parentheses silently mean something else.

**Why it matters in biopharma.** Disposition queries such as 'rejected or under investigation, at 2000 L' drive escalation lists. A precedence slip changes which batches are in scope without any error.

```cypher
MATCH (b:Batch)
WHERE b.status = 'Rejected' OR b.status = 'Under Investigation' AND b.scaleL = 2000
RETURN 'no parentheses' AS form, count(b) AS batches
UNION ALL
MATCH (b:Batch)
WHERE (b.status = 'Rejected' OR b.status = 'Under Investigation') AND b.scaleL = 2000
RETURN 'with parentheses' AS form, count(b) AS batches;
```

**What to expect.** Two rows: 'no parentheses' 2 batches, 'with parentheses' 1 batch. The first form means Rejected (any scale) OR (Under Investigation AND 2000 L).

**Pitfall.** XOR also exists (true when exactly one side is true). Cypher uses <> for not-equal; != is not valid.

**In the manual.** Cypher manual: Predicates > Boolean operators (AND, OR, XOR, NOT) and operator precedence.

### F-03 - IN with lists and chained range comparisons

`beginner`  `read-only`  `exam: Cypher`

**What you learn.** IN tests membership of a list literal, and comparisons chain (200 <= x <= 500), so a range needs no AND.

**Why it matters in biopharma.** Scale classes (50 L bench, 200 L development, 500 L pilot, 2000 L production) are natural lists and ranges; filtering on them is how comparability and scale-up reviews are scoped.

```cypher
MATCH (b:Batch)
WHERE 200 <= b.scaleL <= 500
  AND b.status IN ['Released', 'Rejected']
RETURN b.scaleL AS scaleL, b.status AS status, count(*) AS batches
ORDER BY scaleL, status;
```

**What to expect.** Three rows: (200, Rejected, 1), (200, Released, 3), (500, Released, 9).

**Pitfall.** IN needs a list, not a parenthesised set: b.status IN ('Released') is not a list. A list that contains null never makes IN true for a null value.

**In the manual.** Cypher manual: Predicates > List operators (IN); Operators > Comparison operators (chained).

### F-04 - STARTS WITH, CONTAINS, ENDS WITH and regular expressions

`beginner`  `read-only`  `exam: Cypher`

**What you learn.** There is no LIKE: use STARTS WITH, ENDS WITH and CONTAINS for simple matching, and =~ for a regular expression that must match the whole string.

**Why it matters in biopharma.** Free-text fields such as material names, deviation titles and root causes are searched constantly during investigations ('everything mentioning Resin').

```cypher
MATCH (m:Material)
RETURN count(CASE WHEN m.name STARTS WITH 'CHO'    THEN 1 END) AS startsWithCHO,
       count(CASE WHEN m.name CONTAINS 'Resin'     THEN 1 END) AS containsResin,
       count(CASE WHEN m.name ENDS WITH 'Medium'   THEN 1 END) AS endsWithMedium,
       count(CASE WHEN m.name =~ 'CHO'             THEN 1 END) AS regexNoWildcard,
       count(CASE WHEN m.name =~ '.*CHO.*'         THEN 1 END) AS regexWithWildcard,
       count(CASE WHEN m.name =~ '(?i).*resin.*'   THEN 1 END) AS regexCaseInsensitive;
```

**What to expect.** One row: startsWithCHO 2, containsResin 4, endsWithMedium 2, regexNoWildcard 0, regexWithWildcard 2, regexCaseInsensitive 4.

**Pitfall.** =~ is anchored: m.name =~ 'CHO' is false for 'CHO Feed Medium' because the pattern must match the entire value. Use '.*CHO.*' for 'contains', and the (?i) flag for case-insensitive matching. There is no % wildcard.

**In the manual.** Cypher manual: Predicates > String operators; Operators > Regular expressions.

### F-05 - NULL: missing data is not false

`beginner`  `read-only`  `exam: Cypher`

**What you learn.** A missing property evaluates to null, comparisons with null yield null (not false), WHERE keeps only true, and NOT null is still null - so rows with missing values vanish from both a condition and its negation.

**Why it matters in biopharma.** Real GxP data always has gaps (yield not yet calculated, disposition pending). Reports that silently drop the gaps under-state populations; this is a data-integrity issue, not just a syntax one.

```cypher
MATCH (b:Batch)
RETURN count(*)                                                    AS batches,
       count(b.overallYieldPct)                                    AS withYield,
       count(CASE WHEN b.overallYieldPct > 70 THEN 1 END)          AS above70,
       count(CASE WHEN NOT b.overallYieldPct > 70 THEN 1 END)      AS notAbove70,
       count(CASE WHEN b.overallYieldPct IS NULL THEN 1 END)       AS missing,
       count(CASE WHEN coalesce(b.overallYieldPct, 0) <= 70 THEN 1 END) AS notAbove70IncludingNulls;
```

**What to expect.** One row: batches 29, withYield 26, above70 17, notAbove70 9, missing 3, notAbove70IncludingNulls 12. Note 17 + 9 = 26, not 29.

**Pitfall.** WHERE x > 70 and WHERE NOT x > 70 together miss every row where x is null. Test with IS NULL / IS NOT NULL, never = null, and use coalesce(x, default) when a default is legitimate.

**In the manual.** Cypher manual: Working with null; Functions > Scalar functions (coalesce).

> **Three-valued logic in one table.** Every comparison with `null` returns `null`, and `WHERE` keeps only `true`.
>
> | Expression | Result |
> |---|---|
> | `null = null` | `null` (not true) |
> | `null IS NULL` | `true` |
> | `NOT null` | `null` |
> | `true AND null` | `null` |
> | `false AND null` | `false` |
> | `true OR null` | `true` |
> | `null IN [1, 2]` | `null` |
> | `coalesce(null, 0)` | `0` |
>
> In a regulated data set this is a data-integrity point as much as a syntax one: a missing value is not a pass and
> not a fail, and a filter that does not decide which it is will drop the record without telling anyone.

### F-06 - Label expressions: OR, NOT and AND on labels

`intermediate`  `read-only`  `exam: Cypher`

**What you learn.** A node pattern can match several labels at once with | (either), & (both), ! (not) and parentheses; WHERE n:Label tests a label on an already-bound node.

**Why it matters in biopharma.** Cross-entity searches ('every Batch or CellBank touched by this event') are routine in impact assessment; label expressions avoid UNION-ing near-identical queries.

```cypher
MATCH (n:Batch|CellBank)
RETURN labels(n) AS labels, count(*) AS nodes
ORDER BY nodes DESC;

MATCH (n:!Batch&!Sample)
RETURN count(n) AS everythingElse;
```

**What to expect.** Statement 1: two rows, [Batch] 29 and [CellBank] 11. Statement 2: one row, everythingElse 1099 (1262 nodes minus 29 batches and 134 samples).

**Pitfall.** n:!Batch&!Sample means neither label; n:!(Batch&Sample) means not-both, which is almost every node. Label expressions in MATCH and WHERE are 5.x syntax; Neo4j 4.x had only a single label per pattern element.

**In the manual.** Cypher manual: Patterns > Label expressions.

### F-07 - Patterns as predicates: (a)-[]->() and EXISTS { }

`intermediate`  `read-only`  `exam: Cypher`

**What you learn.** A relationship pattern in WHERE is a true/false test on graph shape; when you need to filter the node at the other end, use EXISTS { MATCH ... WHERE ... }.

**Why it matters in biopharma.** 'Which released batches have no deviation?' and 'which batches are touched by an open deviation?' are the basic questions a QA review asks before certification.

```cypher
MATCH (b:Batch)
WHERE (b)<-[:AFFECTS]-(:Deviation)
RETURN count(b) AS batchesWithDeviation;

MATCH (b:Batch)
WHERE NOT (b)<-[:AFFECTS]-(:Deviation)
RETURN count(b) AS batchesWithoutDeviation;

MATCH (b:Batch)
WHERE EXISTS { (b)<-[:AFFECTS]-(d:Deviation) WHERE d.status = 'Open' }
RETURN b.batchNumber AS batch, b.status AS status
ORDER BY batch;
```

**What to expect.** Statement 1: 8. Statement 2: 21. Statement 3: two rows, BTX101-26-002 and BTX404-26-001.

**Pitfall.** A pattern predicate may not introduce a new variable: WHERE (b)<-[:AFFECTS]-(d:Deviation {status:'Open'}) is rejected. Use EXISTS { (b)<-[:AFFECTS]-(d:Deviation) WHERE d.status = 'Open' } instead.

**In the manual.** Cypher manual: Subqueries > EXISTS subqueries; Predicates > Path pattern expressions.

### F-08 - Direction and relationship uniqueness

`intermediate`  `read-only`  `exam: Cypher`

**What you learn.** An undirected pattern matches each relationship in both orientations, and within one MATCH a relationship is never used twice (nodes can repeat, relationships cannot).

**Why it matters in biopharma.** Cell bank genealogy (MCB to WCB) is a regulatory expectation; counting lineage edges wrongly gives a wrong answer on how many working banks derive from a master bank.

```cypher
MATCH (:CellBank)-[:DERIVED_FROM]->(:CellBank)
RETURN count(*) AS directed;

MATCH (:CellBank)-[:DERIVED_FROM]-(:CellBank)
RETURN count(*) AS undirected;

MATCH (a:CellBank)-[:DERIVED_FROM]-(m:CellBank)-[:DERIVED_FROM]-(c:CellBank)
RETURN count(*) AS twoHopsNoRepeatedRelationship;
```

**What to expect.** Statement 1: 6. Statement 2: 12. Statement 3: 2 (the two working banks derived from MCB-BTX101, in both orders).

**Pitfall.** Leaving the arrow off doubles the row count when both ends are unbound. Within one MATCH pattern nodes may repeat but a relationship may not, so a path never walks the same edge back; across separate MATCH clauses relationships can repeat.

**In the manual.** Cypher manual: Patterns > Match modes (relationship uniqueness / DIFFERENT RELATIONSHIPS).

### F-09 - count(*), count(x), count(DISTINCT x) and null-skipping aggregates

`beginner`  `read-only`  `exam: Cypher`

**What you learn.** count(*) counts rows, count(x) counts non-null values, DISTINCT de-duplicates, and avg/sum/min/max ignore nulls - so avg is not sum divided by the row count.

**Why it matters in biopharma.** A mean yield over 'all batches' that quietly excludes batches without a yield is a different statement from the mean over every batch; continued process verification needs to say which one it reports.

```cypher
MATCH (b:Batch)
RETURN count(*)                                   AS rows,
       count(b.overallYieldPct)                   AS nonNull,
       count(DISTINCT b.status)                   AS statuses,
       round(avg(b.overallYieldPct), 1)           AS avgIgnoresNull,
       round(sum(b.overallYieldPct) / count(*), 1) AS sumOverAllRows,
       min(b.dispositionDate)                     AS firstDisposition,
       collect(DISTINCT b.status)                 AS statusList;
```

**What to expect.** One row: rows 29, nonNull 26, statuses 6, avgIgnoresNull 71.4, sumOverAllRows 64.0, firstDisposition 2024-09-02, statusList containing the six statuses (order not guaranteed).

**Pitfall.** collect() also skips nulls. An aggregate with no grouping key returns exactly one row even on empty input (count 0, others null), unlike a grouped aggregate, which returns no rows.

**In the manual.** Cypher manual: Functions > Aggregating functions.

### F-10 - WITH as pipeline and HAVING

`intermediate`  `read-only`  `exam: Cypher`

**What you learn.** WITH ends one query stage and starts the next: only what it lists stays in scope, and a WHERE after WITH filters aggregated values - Cypher's HAVING.

**Why it matters in biopharma.** Screening populations ('products with at least five lots to date') before a statistical comparison avoids drawing conclusions from two or three runs.

```cypher
MATCH (p:Product)<-[:OF_PRODUCT]-(b:Batch)
WITH p, count(b) AS batches, count(CASE WHEN b.status = 'Released' THEN 1 END) AS released
WHERE batches >= 5
RETURN p.productCode AS product, batches, released
ORDER BY batches DESC;
```

**What to expect.** Three rows: BTX-101 (8 batches, 6 released), BTX-505 (7, 6), BTX-202 (6, 5).

**Pitfall.** Aggregates are not allowed in WHERE after MATCH (WHERE count(b) >= 5 is an error); aggregate in WITH, then filter. Any variable not listed in WITH is gone afterwards.

**In the manual.** Cypher manual: Clauses > WITH.

> **Reading a query for correctness.** Cypher reads top to bottom as a pipeline of stages, and each stage hands a table of
> rows to the next. When you are asked whether a query is right, check in this order:
>
> 1. **What is in scope?** Only variables bound by earlier stages, and after `WITH` only the ones it lists.
> 2. **Where does each `WHERE` attach?** To the `MATCH`, `OPTIONAL MATCH` or `WITH` directly above it - and that decides
>    whether rows are removed or only the optional part is.
> 3. **What does each aggregate ignore?** `null`s, and what are the grouping keys (every other `RETURN`/`WITH` item).
> 4. **What happens to missing data?** Follow a `null` through each condition.
> 5. **What is the row count at each stage?** Joins by pattern multiply rows; aggregation collapses them.
>
> Most wrong answers on both exams and real dashboards come from steps 2 to 4.

### F-11 - ORDER BY, SKIP, LIMIT and where nulls sort

`beginner`  `read-only`  `exam: Cypher`

**What you learn.** ORDER BY sorts nulls last in ascending order and first in descending order; SKIP and LIMIT page the result (SKIP, not OFFSET), and a second sort key makes paging deterministic.

**Why it matters in biopharma.** 'Top five yielding batches' reports are common in product reviews; a top-N list that is led by missing values is a wrong report, not a cosmetic one.

```cypher
MATCH (b:Batch)
RETURN b.batchNumber AS batch, b.overallYieldPct AS yield
ORDER BY yield DESC, batch
LIMIT 5;

MATCH (b:Batch)
WHERE b.overallYieldPct IS NOT NULL
RETURN b.batchNumber AS batch, b.overallYieldPct AS yield
ORDER BY yield DESC, batch
SKIP 0 LIMIT 5;
```

**What to expect.** Statement 1: five rows led by three null yields (BTX101-26-003, BTX303-26-003, BTX505-26-004) then 80.0 and 77.6. Statement 2: the top five real yields starting with 80.0.

**Pitfall.** Descending order puts nulls first, which surprises people coming from databases that sort nulls last. Filter with IS NOT NULL or sort on coalesce(x, -1). Without a tie-breaker, rows with equal keys may come back in a different order between runs.

**In the manual.** Cypher manual: Clauses > ORDER BY, SKIP, LIMIT; Working with null (ordering).

### F-12 - OPTIONAL MATCH: the LEFT JOIN, and where its WHERE belongs

`intermediate`  `read-only`  `exam: Cypher`

**What you learn.** OPTIONAL MATCH keeps the row and returns null when the pattern is absent; a WHERE attached to it filters the optional part only, never the outer rows.

**Why it matters in biopharma.** 'All batches, with their open deviations if any' is the shape of a batch-record review; an inner join would silently remove the clean batches that QA also needs to see.

```cypher
MATCH (b:Batch)
OPTIONAL MATCH (b)<-[:AFFECTS]-(d:Deviation)
RETURN count(*) AS rows, count(d) AS withDeviation;

MATCH (b:Batch)
OPTIONAL MATCH (b)<-[:AFFECTS]-(d:Deviation)
WHERE d.status = 'Open'
RETURN count(*) AS rows, count(d) AS openDeviations;

MATCH (b:Batch)<-[:AFFECTS]-(d:Deviation)
WHERE d.status = 'Open'
RETURN count(*) AS rowsAsInnerJoin;
```

**What to expect.** Statement 1: rows 29, withDeviation 8. Statement 2: rows 29, openDeviations 2. Statement 3: 2.

**Pitfall.** Moving the condition from the OPTIONAL MATCH's WHERE into a later WHERE turns the left join into an inner join. count(*) counts rows including null-extended ones; count(d) counts only matches.

**In the manual.** Cypher manual: Clauses > OPTIONAL MATCH.

### F-13 - UNWIND: lists to rows (and the empty-list trap)

`intermediate`  `read-only`  `exam: Cypher`

**What you learn.** UNWIND turns a list into one row per element - the standard way to feed a list of identifiers or parameters into a query; the inverse of collect().

**Why it matters in biopharma.** Investigators receive lists of batch or lot numbers from a complaint or audit finding; UNWIND plus OPTIONAL MATCH both looks them up and shows which identifiers do not exist.

```cypher
UNWIND ['BTX101-24-001', 'BTX202-24-001', 'NOT-A-BATCH'] AS batchNumber
OPTIONAL MATCH (b:Batch {batchNumber: batchNumber})
RETURN batchNumber, b.status AS status;

UNWIND [] AS nothing
RETURN 'never returned' AS message;
```

**What to expect.** Statement 1: three rows, BTX101-24-001 Released, BTX202-24-001 Released, NOT-A-BATCH null. Statement 2: zero rows.

**Pitfall.** UNWIND of an empty list (or of null) produces no rows, so everything after it vanishes and the query returns nothing without an error. Wrap in OPTIONAL MATCH or guard with coalesce(list, []) when that matters.

**In the manual.** Cypher manual: Clauses > UNWIND.

### F-14 - CASE, integer division and type conversion

`beginner`  `read-only`  `exam: Cypher`

**What you learn.** CASE is an expression (generic or simple form), / on two integers is integer division, ^ always returns a float, and toInteger()/toFloat() return null rather than failing on text that cannot convert.

**Why it matters in biopharma.** Unit and scale arithmetic (volumes, ratios, yields) goes wrong quietly when integer division truncates, and imported CSV text must be converted explicitly.

```cypher
RETURN 5 / 2 AS intDivision, 5 / 2.0 AS floatDivision, 5 % 2 AS modulo, 2 ^ 3 AS power,
       toInteger('12') + 1 AS parsed, toFloat('3.5') AS parsedFloat, toInteger('abc') AS badParse;

MATCH (b:Batch)
RETURN CASE WHEN b.scaleL >= 2000 THEN 'production'
            WHEN b.scaleL >= 500  THEN 'pilot'
            ELSE 'development' END AS scaleClass,
       count(*) AS batches
ORDER BY batches DESC;

MATCH (b:Batch)
RETURN b.status AS status,
       CASE b.status WHEN 'Released' THEN 'final' WHEN 'Rejected' THEN 'final' ELSE 'open' END AS stage,
       count(*) AS batches
ORDER BY batches DESC LIMIT 1;
```

**What to expect.** Statement 1: intDivision 2, floatDivision 2.5, modulo 1, power 8.0, parsed 13, parsedFloat 3.5, badParse null. Statement 2: production 11, pilot 10, development 8. Statement 3: Released 22.

**Pitfall.** 5 / 2 is 2, not 2.5; make one operand a float. LOAD CSV delivers everything as strings, so numeric and date columns need toInteger(), toFloat() or datetime() before comparing or doing arithmetic.

**In the manual.** Cypher manual: Expressions > CASE; Operators > Mathematical operators; Functions > Scalar functions.

### F-15 - UNION and UNION ALL

`beginner`  `read-only`  `exam: Cypher`

**What you learn.** UNION removes duplicate rows across the combined queries, UNION ALL keeps them; the column names and count must match in every arm.

**Why it matters in biopharma.** Governance checks (see TRV-05) are written as one query per rule joined with UNION; knowing which form de- duplicates avoids hiding repeated findings or double-counting them.

```cypher
MATCH (b:Batch {status: 'Rejected'})-[:OF_PRODUCT]->(p:Product) RETURN p.modality AS modality
UNION ALL
MATCH (b:Batch {status: 'Under Investigation'})-[:OF_PRODUCT]->(p:Product) RETURN p.modality AS modality;

MATCH (b:Batch {status: 'Rejected'})-[:OF_PRODUCT]->(p:Product) RETURN p.modality AS modality
UNION
MATCH (b:Batch {status: 'Under Investigation'})-[:OF_PRODUCT]->(p:Product) RETURN p.modality AS modality;
```

**What to expect.** Statement 1 (UNION ALL): 3 rows. Statement 2 (UNION): 2 rows, because 'Monoclonal antibody' appears twice.

**Pitfall.** UNION without ALL sorts out duplicates, which costs a de-duplication step; if the arms cannot overlap, UNION ALL is the cheaper and correct choice. Mixing UNION and UNION ALL in one query is an error.

**In the manual.** Cypher manual: Clauses > UNION.

### F-16 - Shaping results: aliases, DISTINCT, map projection, missing keys

`beginner`  `read-only`  `exam: Cypher`

**What you learn.** RETURN can alias, de-duplicate with DISTINCT, and build maps with projection (b {.a, .b}); reading a property that does not exist returns null instead of an error.

**Why it matters in biopharma.** Result shapes matter when queries feed dashboards or APIs: projecting only the fields a consumer needs keeps payloads small and avoids exposing attributes by accident.

```cypher
MATCH (b:Batch {batchNumber: 'BTX101-24-001'})
RETURN b {.batchNumber, .status, .scaleL} AS summary,
       size(keys(b))                       AS propertyCount,
       b.noSuchProperty                    AS missing;

MATCH (b:Batch)
RETURN DISTINCT b.status AS status
ORDER BY status;
```

**What to expect.** Statement 1: one row with summary {batchNumber, status, scaleL}, propertyCount 9, missing null. Statement 2: six distinct statuses.

**Pitfall.** A misspelled property name is not an error - it is null, so the typo shows up as an empty column or a vanished filter result. Check names against the model (docs/MODEL.md) or SHOW/db.schema output when a result is unexpectedly empty.

**In the manual.** Cypher manual: Clauses > RETURN; Expressions > Map expressions (map projection).

## 02 - Reading the graph

The core of Cypher is pattern matching: you draw the shape you want and the database finds every place it occurs.
This section covers filtering, binding whole paths, and aggregating. Everything later builds on these three moves.

### R-01 - Filter, sort, limit

`beginner`  `read-only`

**What you learn.** Inline property maps filter on equality; the relationship pattern replaces the SQL join.

**Why it matters in biopharma.** Pulling the release history of a product is the raw input to an annual product review and to continued process verification.

```cypher
MATCH (b:Batch {status:'Released'})-[:OF_PRODUCT]->(:Product {productCode:'BTX-101'})
RETURN b.batchNumber, b.scaleL, b.titerGPerL, b.overallYieldPct, b.dispositionDate
ORDER BY b.dispositionDate DESC LIMIT 5;
```

**What to expect.** 5 rows, newest disposition first.

### R-02 - Bind and return a path (cell bank genealogy)

`beginner`  `read-only`

**What you learn.** Assigning a pattern to a variable (path = ...) lets you return the whole route; switch the result to graph view to see it.

**Why it matters in biopharma.** Cell-substrate history (master bank, working bank, production batch) is the root of traceability for a biologic. Regulators expect every lot to be traceable to its cell bank (see ICH Q5D on cell substrates).

```cypher
MATCH path = (:Batch {batchNumber:'BTX101-24-001'})-[:INOCULATED_FROM]->(:CellBank)
             -[:DERIVED_FROM]->(:CellBank)-[:EXPRESSES]->(:Product)
RETURN path;
```

**What to expect.** One path: batch -> working cell bank -> master cell bank -> product.

### R-03 - Implicit grouping: yield by product and scale

`beginner`  `read-only`

**What you learn.** Every non-aggregated column in RETURN becomes a grouping key; there is no GROUP BY clause.

**Why it matters in biopharma.** Comparing titer and downstream yield across scales is basic process-development analytics, and the starting point of a scale-up or comparability discussion (ICH Q11, ICH Q5E).

```cypher
MATCH (p:Product)<-[:OF_PRODUCT]-(b:Batch)
WHERE b.overallYieldPct IS NOT NULL
RETURN p.productCode AS product, b.scaleL AS scaleL, count(b) AS batches,
       round(avg(b.titerGPerL),2) AS avgTiter, round(avg(b.overallYieldPct),1) AS avgYield
ORDER BY product, scaleL;
```

**What to expect.** One row per product and scale combination that has completed batches.

> **Why does this data suit a graph?**
> A batch record touches cell banks, a vessel, a recipe, dozens of material lots, samples, results, people and
> deviations. In tables every question is a different multi-way join, and every new question means re-planning the join.
> In a graph the relationships are stored data, so the same traversal that answers "genealogy of one batch" (R-02) also
> answers "every batch that used this resin lot" (TRV-04) by walking the same edges the other way. The trade-off is real:
> wide aggregations over millions of flat rows are usually faster in a columnar engine, which is why production
> architectures often use both (see the note after ANA-05).

## 03 - Subqueries and per-row logic

Modern Cypher has subquery expressions (`COUNT {}`, `EXISTS {}`, `COLLECT {}`) and scoped `CALL` blocks.
They avoid the row-multiplication traps of chaining `OPTIONAL MATCH` and make per-group logic readable.

### SUB-01 - Count subqueries

`intermediate`  `read-only`

**What you learn.** COUNT { pattern } counts matches per row without multiplying rows - the modern replacement for OPTIONAL MATCH followed by count().

**Why it matters in biopharma.** Batch record review is review-by-exception: you want to see quickly which batches carry deviations and how much testing exists per batch.

```cypher
MATCH (b:Batch)
RETURN b.batchNumber AS batch, b.status AS status,
       COUNT { (b)<-[:AFFECTS]-(:Deviation) } AS deviations,
       COUNT { (b)<-[:TAKEN_FROM]-(:Sample) } AS samples
ORDER BY deviations DESC, batch LIMIT 10;
```

**What to expect.** 10 rows; batches with deviations first.

### SUB-02 - Collect subquery: OOS attributes per batch

`intermediate`  `read-only`

**What you learn.** COLLECT { MATCH ... RETURN x } builds a per-row list; filtering on size() of that list keeps only rows that have matches.

**Why it matters in biopharma.** Out-of-specification results must be investigated before disposition (FDA guidance on investigating OOS results). A per-batch OOS summary is what a disposition meeting looks at; invalidated results appear next to confirmed ones so nothing is hidden.

```cypher
MATCH (b:Batch)
WITH b, COLLECT {
  MATCH (b)<-[:TAKEN_FROM]-(:Sample)<-[:ON_SAMPLE]-(t:TestResult {outcome:'OOS'})-[:AGAINST_SPEC]->(s:Specification)
  RETURN s.attribute + ' (' + t.resultStatus + ')'
} AS oosAttributes
WHERE size(oosAttributes) > 0
RETURN b.batchNumber, b.status, oosAttributes;
```

**What to expect.** 4 batches: two Released (OOS invalidated, retest passed), one Rejected (confirmed), one Under Investigation (open).

### SUB-03 - Top-N per group with a scoped CALL

`advanced`  `read-only`  `needs Neo4j 5.23+ (older: CALL { WITH p ... })`

**What you learn.** CALL (p) { ... LIMIT 2 } runs the LIMIT once per product; a plain LIMIT would cut the whole result.

**Why it matters in biopharma.** Continued process verification looks at the most recent few batches of each product, not the global latest N. Per-group top-N is a pattern you will need constantly.

```cypher
MATCH (p:Product)
CALL (p) {
  MATCH (p)<-[:OF_PRODUCT]-(b:Batch)<-[r:PRODUCES]-(:Bioreactor)
  RETURN b, r.startTime AS started
  ORDER BY started DESC LIMIT 2
}
RETURN p.productCode, b.batchNumber, b.status, started
ORDER BY p.productCode, started DESC;
```

**What to expect.** Up to 2 rows per product (10 rows).

## 04 - Traversal, lineage and impact analysis

This is where graph databases earn their keep: variable-length paths, "everything downstream of X", shortest paths,
and forward/backward traceability. In biopharma these map directly to genealogy, change impact and recall questions.

### TRV-01 - Variable-length path: reconstruct an ordered recipe

`intermediate`  `read-only`

**What you learn.** -[:FOLLOWED_BY*]-> walks any number of hops; NOT (last)-[:FOLLOWED_BY]->() finds the end of the chain; list comprehensions reshape nodes(path).

**Why it matters in biopharma.** A purification process is an ordered sequence of unit operations defined in a controlled document. Reading it back from the data confirms that the electronic recipe matches the approved document (recipe verification).

```cypher
MATCH (:PurificationProtocol {protocolId:'SOP-DSP-0101-v2.0'})-[:INCLUDES]->(first:PurificationStep {stepNumber:1})
MATCH path = (first)-[:FOLLOWED_BY*]->(last:PurificationStep)
WHERE NOT (last)-[:FOLLOWED_BY]->()
RETURN [n IN nodes(path) | toString(n.stepNumber) + '. ' + n.stepName] AS sequence, length(path) AS hops;
```

**What to expect.** One row: 8 steps joined in order (7 hops), from harvest clarification to final filtration and bulk fill.

### TRV-02 - Quantified shorthand: everything downstream of a step

`intermediate`  `read-only`  `needs Neo4j 5.9+`

**What you learn.** ->+ means "one or more hops"; it is the modern spelling of *1.. and the building block for impact analysis.

**Why it matters in biopharma.** If Protein A capture changes, which later unit operations (viral inactivation, polishing, viral filtration, formulation) are affected? That is exactly the question change control asks when assessing risk (ICH Q9) under a quality system (ICH Q10).

```cypher
MATCH (a:PurificationStep {stepId:'SOP-DSP-0505-v2.0-S02'})-[:FOLLOWED_BY]->+(d:PurificationStep)
RETURN d.stepNumber, d.stepName ORDER BY d.stepNumber;
```

**What to expect.** 6 rows: steps 3 to 8 of the BTX-505 v2.0 process.

### TRV-03 - Shortest path (always bound it)

`intermediate`  `read-only`

**What you learn.** shortestPath() finds the fewest-hop route; the [*..5] bound is what keeps it safe on a dense graph.

**Why it matters in biopharma.** Investigations trace a result back to the equipment and batch that produced it. Bounded traversals are cheap; an unbounded variable-length search over a connected manufacturing graph can touch most of the database.

```cypher
MATCH (t:TestResult {resultId:'R-000001'}), (br:Bioreactor)
MATCH p = shortestPath((t)-[*..5]-(br))
RETURN br.equipmentId AS bioreactor, length(p) AS hops, [n IN nodes(p) | labels(n)[0]] AS route
ORDER BY hops LIMIT 1;
```

**What to expect.** One row: 3 hops (TestResult -> Sample -> Batch <- Bioreactor). Run EXPLAIN and find the CartesianProduct operator.

### TRV-04 - Forward impact trace: the recall question

`intermediate`  `read-only`

**What you learn.** Start at a flagged node, traverse forward through relationships carrying properties (quantity, unit), and aggregate what you find.

**Why it matters in biopharma.** When a supplier notifies you about a raw-material or resin lot, you must identify every batch of every product made with it, within hours. Forward traceability is a core GMP material-control expectation; this is the query graphs exist for.

```cypher
MATCH (l:MaterialLot {status:'Supplier Notification'})-[:LOT_OF]->(m:Material)
MATCH (l)<-[c:CONSUMED]-(b:Batch)-[:OF_PRODUCT]->(p:Product)
OPTIONAL MATCH (b)<-[:TAKEN_FROM]-(:Sample {sampleType:'Release'})<-[:ON_SAMPLE]-(t:TestResult {resultStatus:'Valid'})
RETURN m.name AS material, l.lotNumber AS lot, p.productCode AS product, b.batchNumber AS batch,
       b.status AS status, c.quantity + ' ' + c.unit AS used,
       count(t) AS releaseResults, sum(CASE WHEN t.outcome = 'OOS' THEN 1 ELSE 0 END) AS oos
ORDER BY batch;
```

**What to expect.** 6 rows: the batches that consumed lot L24-011-003 (the Protein A resin lot flagged Supplier Notification), all Released, with how many release results each has and how many were OOS.

### TRV-05 - Governance assertions (every row is a violation)

`advanced`  `read-only`

**What you learn.** UNION of independent rule checks, each returning (violation, entity); NOT EXISTS {} expresses a missing relationship.

**Why it matters in biopharma.** Data-integrity rules written as executable checks: a released batch must have a QA approver, must not carry a valid OOS result, and second-person review must be independent of the performer. Running these on a schedule is how a data product demonstrates it is under control (in the spirit of 21 CFR Part 11 and the ALCOA+ principles).

```cypher
MATCH (b:Batch {status:'Released'})
WHERE NOT EXISTS { (b)<-[:RESPONSIBLE_FOR {role:'QA Approver'}]-(:Employee) }
RETURN 'released without QA approver' AS violation, b.batchNumber AS entity
UNION
MATCH (b:Batch {status:'Released'})<-[:TAKEN_FROM]-(:Sample)<-[:ON_SAMPLE]-(:TestResult {outcome:'OOS', resultStatus:'Valid'})
RETURN 'released with valid OOS' AS violation, b.batchNumber AS entity
UNION
MATCH (a:Employee)<-[:PERFORMED_BY]-(t:TestResult)-[:REVIEWED_BY]->(a)
RETURN 'self-reviewed result' AS violation, t.resultId AS entity;
```

**What to expect.** 0 rows. Any row is a violation that needs a deviation.

> **Queries as controls (ALCOA+).**
> Data-integrity expectations are usually summarised as ALCOA+: records are *Attributable, Legible, Contemporaneous,
> Original, Accurate*, plus *Complete, Consistent, Enduring, Available*. Several map onto this model directly:
> `PERFORMED_BY` / `REVIEWED_BY` (attributable), `testedAt` / `reviewedAt` (contemporaneous), deviations and retests that
> are *added* instead of overwriting results (original, enduring), the reconciliation counts in O-02 (complete).
> TRV-05 shows the pattern: express a rule as a query, run it on a schedule, and treat every returned row as an event to
> investigate. This is a teaching dataset, not a validated system, and nothing here is regulatory advice.

## 05 - Analytics in Cypher

Trends, durations, statistics and profiling. Cypher has no window functions, but `collect()` plus list comprehensions,
temporal types and the built-in statistical aggregates cover a lot of practical ground.

### ANA-01 - Run-to-run trend without window functions

`advanced`  `read-only`

**What you learn.** ORDER BY, then collect(), then a list comprehension over range() replaces LAG() for simple deltas.

**Why it matters in biopharma.** Trending yield across consecutive batches surfaces step changes after a process or material change, which is the core of continued process verification.

```cypher
MATCH (p:Product)<-[:OF_PRODUCT]-(b:Batch)<-[r:PRODUCES]-()
WHERE b.overallYieldPct IS NOT NULL
WITH p, b, r ORDER BY r.startTime
WITH p, collect(b.overallYieldPct) AS y
RETURN p.productCode, y, [i IN range(1, size(y)-1) | round(y[i] - y[i-1], 1)] AS deltas;
```

**What to expect.** One row per product with completed batches: the yield list in start order and the batch-to-batch deltas.

### ANA-02 - Durations from temporal properties

`intermediate`  `read-only`

**What you learn.** datetime properties are real temporal types: duration.between(a, b).days works, and date(x).year etc. are available for roll-ups.

**Why it matters in biopharma.** Culture duration and hold times are capacity-planning inputs and leading indicators of process drift.

```cypher
MATCH (br:Bioreactor)-[r:PRODUCES]->(:Batch)
WHERE r.endTime IS NOT NULL
WITH br.nominalVolumeL AS scaleL, duration.between(r.startTime, r.endTime) AS d
RETURN scaleL, count(*) AS runs, round(avg(d.days),1) AS avgCultureDays, min(d.days) AS minDays, max(d.days) AS maxDays
ORDER BY scaleL;
```

**What to expect.** 4 rows (50, 200, 500 and 2000 L), runs ordered by scale, with roughly 12-16 day cultures.

### ANA-03 - Statistics and process capability

`advanced`  `read-only`

**What you learn.** stDev() and percentileCont() are built-in aggregates; a one-sided capability index can be computed against the limit stored in the graph.

**Why it matters in biopharma.** Capability against specification limits is routine in continued process verification and in setting specifications for biotechnological products (ICH Q6B). Conventionally an index below about 1.33 draws attention. Caveat: it assumes enough batches and roughly normal data; with a handful of batches per product treat it as a screening number.

```cypher
MATCH (t:TestResult {resultStatus:'Valid'})-[:AGAINST_SPEC]->(s:Specification {attribute:'High Molecular Weight Species', stage:'Release'})-[:APPLIES_TO]->(p:Product)
WITH p.productCode AS product, s.upperLimit AS usl, count(t) AS n,
     avg(t.value) AS mean, stDev(t.value) AS sd, percentileCont(t.value, 0.95) AS p95
RETURN product, n, round(mean,2) AS mean, round(sd,2) AS sd, round(p95,2) AS p95, usl,
       CASE WHEN sd > 0 THEN round((usl - mean) / (3 * sd), 2) END AS ppkUpper
ORDER BY ppkUpper;
```

**What to expect.** One row per product, ordered by ppkUpper ascending (lowest capability first).

### ANA-04 - Relationship-property math: medium per gram of product

`intermediate`  `read-only`

**What you learn.** Facts such as quantity and unit live on the CONSUMED relationship, so aggregate over r.property directly.

**Why it matters in biopharma.** Material consumption per gram of drug substance feeds cost-of-goods and process-efficiency metrics (for example process mass intensity).

```cypher
MATCH (p:Product)<-[:OF_PRODUCT]-(b:Batch)-[c:CONSUMED]->(:MaterialLot)-[:LOT_OF]->(:Material {name:'CHO Production Basal Medium'})
WHERE b.drugSubstanceG IS NOT NULL
RETURN p.productCode AS product, count(b) AS batches,
       round(sum(c.quantity) / sum(b.drugSubstanceG), 2) AS mediumLitersPerGramDS
ORDER BY mediumLitersPerGramDS;
```

**What to expect.** One row per product, ordered by liters of medium per gram.

### ANA-05 - Profile property coverage

`beginner`  `read-only`

**What you learn.** keys(n) returns the property names present on a node; unwinding and counting profiles completeness for any label.

**Why it matters in biopharma.** Completeness profiling is the first step in judging a data product's fitness for use. Structural gaps (an in-process batch has no drug-substance mass yet) differ from quality gaps (a released batch missing its disposition date).

```cypher
MATCH (b:Batch) UNWIND keys(b) AS k RETURN k, count(*) AS populated ORDER BY populated;
```

**What to expect.** 9 rows, one per Batch property. batchNumber, gmpStatus, status and scaleL are on all 29 batches; harvestVolumeL (28), drugSubstanceG (26), overallYieldPct (26) and dispositionDate (23) are lower because in-flight batches do not have them yet.

> **Where Cypher stops, and what to pair it with.**
> Graph traversal and relationship-heavy questions belong in Neo4j; large flat aggregations, ML feature engineering
> and heavy statistics usually belong in a lakehouse engine (Spark / SQL on Databricks). The usual production shape is both:
> the graph holds the connected, governed entities and lineage; the lakehouse holds the wide tables; and the two
> exchange data in batches (Neo4j has a Spark connector for this; check its current version and Aura compatibility
> before designing around it). Part of designing a data product is deciding which question goes where.

## 06 - Writing safely

Reads are forgiving; writes are where data products go wrong. This section covers constraints, idempotent upserts,
atomic versioning and invariant checks. **Every query here changes the graph** except WRI-04, so each has an `@undo`.
The undo statements exist only because this is a scratch copy of synthetic data: in a real regulated system you close
or supersede records, you never delete them (see the note after WRI-04).

### WRI-01 - Let a constraint reject you

`beginner`  `writes data`

**What you learn.** CREATE always inserts; the uniqueness constraint is the only thing stopping a duplicate. Its backing index is also what makes MERGE fast.

**Why it matters in biopharma.** Unique identification of records is a basic data-integrity expectation. The same error that blocks a duplicate lab ID blocks a duplicate batch number, and it is the error class you met during the original import.

```cypher
CREATE (:Lab {labId:'QC-MICRO', name:'Duplicate on purpose'});
SHOW CONSTRAINTS YIELD name, labelsOrTypes, properties WHERE 'Lab' IN labelsOrTypes;
```

**What to expect.** The CREATE fails with a ConstraintValidationFailed error naming labId = QC-MICRO. SHOW CONSTRAINTS then lists the constraint on Lab.

**Undo.**
```cypher
none: the CREATE is rejected by the constraint, so nothing is written.
```

### WRI-02 - Idempotent upsert with MERGE

`intermediate`  `writes data`

**What you learn.** MERGE finds-or-creates on the whole pattern; merge on the key only, put everything else in ON CREATE / ON MATCH SET.

**Why it matters in biopharma.** Pipelines must be safe to re-run: the nightly LIMS sync must never create a second copy of a deviation. Merging on identity and setting attributes separately is the standard way to get that.

```cypher
MATCH (b:Batch {batchNumber:'BTX101-24-001'})
MERGE (d:Deviation {deviationId:'DEV-TEST-001'})
  ON CREATE SET d.deviationType='Process Deviation', d.title='Training exercise', d.severity='Minor',
                d.status='Open', d.openedDate=datetime()
  ON MATCH  SET d.lastTouched=datetime()
MERGE (d)-[:AFFECTS]->(b)
RETURN d, b;
```

**What to expect.** One Deviation (DEV-TEST-001) linked to the batch; run it twice and the count stays at one, with lastTouched set on the second run. Afterwards the batch is Released with an Open deviation, which breaks the rule in TRV-05-style checks.

**Undo.**
```cypher
MATCH (d:Deviation {deviationId:'DEV-TEST-001'}) DETACH DELETE d;
```

### WRI-03 - Versioned supersede in one transaction

`advanced`  `writes data`

**What you learn.** One statement is one atomic transaction; the status filter in the MATCH makes a second run a no-op, and the unique protocolId constraint backs that up.

**Why it matters in biopharma.** A controlled document has exactly one effective version at a time, with no gap and no overlap; revising it must be atomic. The SUPERSEDES chain keeps the full history that an audit trail needs.

```cypher
MATCH (old:PurificationProtocol {protocolId:'SOP-DSP-0101-v2.0', status:'Effective'})
CREATE (new:PurificationProtocol {protocolId:'SOP-DSP-0101-v3.0', documentNumber:old.documentNumber, name:old.name,
        version:'3.0', status:'Effective', effectiveDate:datetime('2026-11-01T00:00:00Z'), description:'Training exercise'})
CREATE (new)-[:SUPERSEDES]->(old)
SET old.status='Superseded', old.supersededDate=new.effectiveDate
RETURN old.protocolId, old.status, new.protocolId, new.status;
```

**What to expect.** First run: one row (v2.0 Superseded, v3.0 Effective). Second run: no rows. v3.0 is a stub with no steps, which is why the undo exists. Remove anything you attach to v3.0 before running the undo, or it is left orphaned.

**Undo.**
```cypher
MATCH (new:PurificationProtocol {protocolId:'SOP-DSP-0101-v3.0'})-[:SUPERSEDES]->(old)
SET old.status='Effective', old.supersededDate=null
DETACH DELETE new;
```

### WRI-04 - Check an invariant the database cannot enforce

`intermediate`  `read-only`

**What you learn.** Cypher constraints cannot express "exactly one"; a grouped query that returns violations does, and it can run on a schedule.

**Why it matters in biopharma.** Cardinality rules on controlled documents (one effective version per document number) are data- quality monitors. Schedule the query and alert on any returned row.

```cypher
MATCH (p:PurificationProtocol {status:'Effective'})
WITH p.documentNumber AS doc, collect(p.protocolId) AS effective
WHERE size(effective) <> 1
RETURN doc, effective;
```

**What to expect.** 0 rows, both before and after WRI-03. To see it fire, run WRI-03 without its SET line.

> **Three words that get confused.**
>
> | Property | Meaning | Example here |
> |---|---|---|
> | **Idempotent** | Running it twice leaves the same state as running it once | WRI-02 (`MERGE` on the key) |
> | **Atomic** | It fully happens or does not happen at all | WRI-03 (one statement, one transaction) |
> | **Reversible** | You can get back to the previous state | The `@undo` blocks, which exist only for scratch data |
>
> Idempotency says nothing about whether the *first* run should have happened. WRI-02 cannot create a duplicate, but its
> first run still leaves an open deviation on a released batch.

> **In production: close, supersede, never delete.**
> A regulated record keeps every state it passed through. A deviation moves to *Closed* with a root cause and a
> closing date; a protocol is *Superseded* with dates. The delete statements in the undo blocks would be unthinkable
> on a real deviation or batch record. Atomic transactions and unique constraints protect a single write; they do not
> protect two people running the same revision at once, which is why the WRI-04-style check stays in place as a backstop.

## 07 - Loading and performance

How data gets in at volume, and how to read what the planner is doing. The Aura Importer is ideal for prototyping a model;
production pipelines script the load so it is repeatable, testable and reviewable.

### LOD-01 - LOAD CSV in batched transactions

`advanced`  `writes data`  `needs Neo4j 5.23+`

**What you learn.** Everything in a CSV is a string until converted; create constraints first, MERGE on the key, and batch with IN TRANSACTIONS.

**Why it matters in biopharma.** This is how scripted pipelines land data so a re-run is safe. The Importer is for one-off loads and model prototyping; anything that runs on a schedule should be code in a repository with tests.

```cypher
LOAD CSV WITH HEADERS FROM 'https://<your-public-url>/test_results.csv' AS row
CALL (row) {
  MERGE (t:TestResult {resultId: row.resultId})
  SET t.attempt = toInteger(row.attempt), t.value = toFloat(row.value), t.testedAt = datetime(row.testedAt)
} IN TRANSACTIONS OF 500 ROWS;
```

**What to expect.** Does not run as written: it needs the CSV hosted at a public URL. Replace the placeholder; you may need the :auto prefix in some clients.

**Undo.**
```cypher
none: MERGE on existing keys rewrites the same values when the CSV matches the loaded data.
```

### LOD-02 - Read a query plan with PROFILE

`advanced`  `writes data`

**What you learn.** PROFILE runs the query and reports operators and db hits: a unique-index seek, a label scan, then an index seek once an index exists.

**Why it matters in biopharma.** Performance is a feature of a data product. A real LIMS holds millions of results, so learn to read plans on a small dataset before the data is a thousand times larger. If you ran cypher/post_load.cypher section C, an outcome index already exists: drop TestResult_outcome_idx first to see the contrast.

```cypher
PROFILE MATCH (b:Batch {batchNumber:'BTX101-24-001'}) RETURN b;
PROFILE MATCH (t:TestResult {outcome:'OOS'}) RETURN count(t);
CREATE INDEX tr_outcome_probe IF NOT EXISTS FOR (t:TestResult) ON (t.outcome);
PROFILE MATCH (t:TestResult {outcome:'OOS'}) RETURN count(t);
```

**What to expect.** Plan 1: NodeUniqueIndexSeek. Plan 2: NodeByLabelScan. Plan 3: NodeIndexSeek. With very small data the planner may still choose a scan; compare the db hits.

**Undo.**
```cypher
DROP INDEX tr_outcome_probe IF EXISTS;
```
